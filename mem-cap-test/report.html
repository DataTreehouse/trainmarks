maplib in-memory — how it behaves with less RAM

Running the in-memory maplib workload under a hard Docker memory cap (kernel OOM-kills if exceeded; swap disabled). The question: how does it cope as available memory shrinks?
maplib 0.20.26 (open-source pip build) · datasets 100K / 1M / 10M triples · cap applies to the whole process (Python + maplib + Arrow)
Verdict: in-memory maplib is all-or-nothing — it either fits its full working set in RAM or the kernel kills it; there is no graceful slowdown or spill to disk. For 10M triples the floor is ~3.5 GB (fails at 3 GB, succeeds at 3.5 GB). And the query phase, not loading, sets the floor: at 3 GB it loaded all the data but was killed running the SPARQL queries.

2. Why 3 GB dies: it's the query phase

Peak memory at each operation over the 10M graph. At 3 GB the reads all finish (~3 GB), then the very first query pushes it over the cap and the process is killed — the line stops. At 3.5 GB the same queries fit and it runs to the end.

3. Memory grows with data

Peak memory by dataset size (measured at the 4 GB cap). Roughly linear in triple count — which is exactly why a fixed machine hits a wall as graphs grow.

This is the in-memory engine specifically; the disk-backed maplib variant exists precisely to trade this hard RAM wall for bounded memory at the cost of speed.
